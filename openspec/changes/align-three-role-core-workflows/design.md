# Design

## Context

参见 `proposal.md`。第一步已落地竞赛专用的 `CompetitionWorkflow.vue`、`TeacherCompetitionReview.vue`、规则包和审核计分用例；但实施后在真实本地环境复核发现，竞赛学生页仍是压缩的契约壳，缺少产品级布局与完整状态，且新鲜数据库没有准备可用的 current 规则包，导致目录请求 404、页面无法提交。既有前端证据以 pure helper、源码字符串和构建为主，没有证明 Vue 页面真实挂载或浏览器闭环。因此这些页面不能作为本 change 的已完成依赖，须先由 `repair-2028-competition-workflow-acceptance` 修复并验收。

同时，旧 `ApplicationForm.vue`、`RuleManagement.vue` 和 `ScoreManagement.vue` 仍保留前端选规则、直接编辑规则/成绩以及混合新旧来源的交互。后端 `ranking.py` 已具备 draft、freeze、publish、withdraw 和 successor 的核心能力，但前端没有按管理员、教师、学生职责形成完整入口，且状态命令尚需统一幂等与解冻语义。

本 change 跨越前端路由、角色页面、规则包生命周期、计分快照和排名批次，因此需要保持模块化单体中的清晰依赖：页面 → 角色 API adapter → Blueprint 契约 → 用例层 → 领域策略/持久化。页面不得直接组合多个写接口来完成一个业务动作。

## Goals / Non-Goals

**Goals:**

- 让三个角色基于同一后端快照和状态语义工作，差异只体现在可见范围与允许动作。
- 将 2029 规则维护建模为 2028 已发布包的可审计复制、差异编辑和整体发布。
- 将排名从已有后端能力提升为管理员可完整操作、教师可完整只读、学生可看个人结果的闭环。
- 移除新链路前端中的权威业务字段和本地规则映射，同时保留非竞赛旧流程的清晰兼容边界。
- 让所有三角色页面复用产品级页面结构与状态组件，并以真实挂载测试和新鲜数据库浏览器旅程证明可用性。

**Non-Goals:**

- 不将非竞赛类别迁移到 `MaterialRecord`，也不删除旧 `Application` 表或全部旧页面。
- 不修改竞赛正式分值和特殊计分算法。
- 不允许教师管理规则、执行重算或改变排名状态。
- 不用前端缓存、浏览器时间或本地排序替代后端快照。

## Decisions

### 1. 以“后端返回展示模型 + allowed_actions”统一三角色页面

后端为材料、计分、规则包和排名批次返回稳定的 presentation DTO：对象标识、版本、状态、时间、来源/范围、可见字段、`allowed_actions` 和稳定 reason code。角色查询共享同一权威快照装配器，再由后端按角色和组织范围裁剪，而不是由三个页面分别拼接旧接口。

前端建立薄的角色 API adapter 和共享状态/错误文案映射。按钮由 `allowed_actions` 渲染，但所有写端点继续独立鉴权和状态校验。替代方案是只在路由 meta 和页面条件中控制权限；它无法阻止伪造请求，也容易让页面与后端状态机漂移，因此不采用。

### 2. 新旧前端按材料类别明确分流，不做“大爆炸”重写

学生选择 `competition` 时只进入 `CompetitionWorkflow` 和材料 API；其他类别暂时进入标记为 compatibility 的旧表单。共享导航可统一，但请求 DTO、stores 和服务文件不混用。服务层增加开发期断言/测试，保证竞赛请求不出现 `rule_id`、`self_score`、`final_score`、`dynamic_coefficients`、`override_score`、`override_reason`。

教师竞赛审核继续使用专用只读上下文；旧类别审核页面保留到后续迁移。管理员旧规则列表只用于尚未迁移类别，竞赛规则包管理使用独立页面与端点。这样避免为视觉统一而再次把不同事实模型耦合。

退出兼容期的条件保持不变：所有材料类别完成新模型迁移、旧来源与新明细对账为零差异、没有旧入口写入后，才能在独立 change 删除旧路径。

### 3. 规则包采用 draft revision，而不是复制为大量可变正式 Rule

复制命令输入 `source_package_id`、`target_cycle`、版本和幂等键；用例在单事务中深复制目录、矩阵、字段 schema 与特殊政策，记录来源摘要，并创建 `draft` revision。草稿每次保存产生递增 revision 或不可变内容快照，便于结构化 diff 和并发控制。

差异服务按稳定目录标识和政策路径输出 added/removed/changed，不依赖文本 diff。发布命令重新执行完整校验，在事务中创建不可变 published 版本并设置目标周期唯一 current。若替换当前周期，则调用第一步已有的影响预览与重新确认用例；通知仍通过可重试 outbox，发送失败不回滚发布与失效事实。

不允许在现有 `RuleManagement.vue` 中继续对已发布竞赛规则逐条启停或删除，因为这会破坏规则包原子性。旧 `Rule` 管理仅保留给明确的兼容类别。

### 4. 排名批次以显式状态机和命令端点管理

采用状态转换：`draft → frozen → published → withdrawn`，输入变化可使 `draft → stale`；新增 `frozen → correction_required`（用户界面称“解冻纠错”），之后不能原地编辑条目，只能修正权威来源并生成新 `draft`。已发布版本绝不解冻或覆盖，只能 `published → withdrawn` 后创建 successor。

生成 draft 的范围包括周期、学院、专业、截止时间和精度。冻结同步校验输入 digest、资格、快照、规则版本和迁移对账；发布同步写状态和审计。每个改变状态的命令包含 `version` 与 `idempotency_key`，在一个事务内完成状态、事件和必要快照写入。导出审计可异步记录文件生成，但批次状态不能依赖异步任务成功。

学生查询只从当前允许展示的批次中提取本人 `RankingEntry` 和总人数；教师/管理员查询完整 entries，但只有管理员 DTO 带状态命令。教师发现错误属于线下/系统外反馈，不新增教师修改接口。

### 5. 计分管理页改为“来源、快照、重算命令”，不再编辑派生列

`ScoreManagement.vue` 中综合成绩、学术专长汇总、综合表现汇总、专业排名和排名人数改为只读，并展示快照版本、更新时间和状态。可编辑范围仅保留真正的权威基础数据且通过独立契约校验；派生值不能夹带在学生资料更新 DTO。

管理员重算分为 dry-run 和 execute 两个用例。dry-run 返回范围、输入摘要、预计变化、失败对象和会失效的 draft 批次；execute 必须引用未过期 preview token/摘要并在后端完成有界批次处理与审计。若现有实现不能保证全范围单事务，则响应必须明确逐对象结果与整体 incomplete 状态，不能报告整体成功。

### 6. 前端信息架构围绕任务而非数据库表

学生导航聚合为“提交材料—我的材料—加分统计—我的排名”；教师聚合为“待审核—审核历史—学生汇总—专业排名”；管理员聚合为“规则包—计分与重算—排名发布”。页面组件共享状态徽标、版本冲突处理、阻塞项列表、审计时间线和只读明细表，但不共享业务写表单。

每个命令页面遵循“查看影响 → 确认 → 单次命令 → 读取新状态”。前端不串联“生成后立即冻结再发布”，也不在成功响应前乐观改变权威状态。版本冲突统一刷新并提示用户重新确认影响。

### 7. API 契约和旧端点采取渐进收紧

先新增角色化查询与命令端点并迁移页面，再将旧端点中的派生字段标记 deprecated、记录调用监控并拒绝新工作流来源。竞赛相关冗余字段立即从前端请求删除，后端保留明确拒绝。非竞赛旧端点在兼容期不扩展新功能。

OpenAPI/接口文档必须说明每个 DTO 的权威性、版本字段、幂等键、状态与权限；契约测试验证学生响应不含他人 entries、教师响应不含管理 actions、管理员响应不接受派生字段直接写入。

### 8. 共享产品级页面结构，但不共享业务权威判断

三角色页面复用设计系统中的页面标题/上下文区、状态摘要、筛选与主内容、阻塞项、字段级错误、命令确认、审计时间线和反馈组件。每个页面必须显式处理 loading、empty、success、validation、permission、version conflict 与 actionable error，并在桌面和窄屏维持清晰层级、键盘可达和错误聚焦。

共享组件只消费后端 presentation DTO 和 `allowed_actions`，不推导周期、规则、分数、排名状态或权限。不能通过给现有裸表单增加间距来宣称产品化完成；组件测试必须挂载真实页面/关键子树并执行用户交互。

### 9. 运行依赖就绪是页面入口和验收的前置条件

页面加载时先读取后端权威上下文，确认当前周期、规则包、组织范围、批次或其他必要依赖。缺失依赖时展示稳定 reason code 对应的责任范围与修复动作，不渲染必然失败的伪可用表单。页面控制器统一拥有上下文与记录加载，避免父子组件重复请求和散落的硬编码周期。

本地准备必须从新鲜数据库幂等创建所需政策/规则包，或在启动前明确失败；“数据库结构正确但业务依赖为空”不算可用环境。change2 在 corrective change 未通过此门槛前，不得把竞赛链路视作稳定依赖。

### 10. 验收采用契约、挂载组件、真实浏览器三层证据

第一层用后端和 pure frontend tests 验证 DTO、权限、状态与 adapter；第二层用真实挂载的 Vue 组件测试验证 DOM、交互、错误、焦点和请求编排；第三层删除并重建本地数据库，通过正式启动脚本连接实际后端，在浏览器完成学生、教师、管理员关键旅程并保存路由、网络响应、截图和最终权威状态。

构建和源码断言只证明编译或静态边界，不能标作 component/E2E/visual acceptance。OCR 成功路径、生产数据库、其他浏览器或平台若未执行，必须明确记录为 skipped/unavailable。

## Risks / Trade-offs

- [第二步同时涉及规则和排名，页面范围较大] → 以后端契约、规则包、排名命令、三个角色页面的依赖顺序实施，每组独立验收，避免先做视觉重写。
- [旧页面仍可能调用废弃写接口] → 增加端点调用监控、契约拒绝和请求快照测试；完成迁移后删除对应前端方法，而不是只隐藏按钮。
- [复制规则包会把旧错误带到新周期] → 强制结构化 diff、完整校验和人工发布确认；复制只产生草稿，绝不自动 current。
- [“解冻”容易被理解为原地修改冻结名单] → 使用内部 `correction_required` 状态，禁止编辑 entries，必须修正来源并新建 draft。
- [教师完整排名可能泄露到未授权学院/专业] → 后端按组织范围鉴权，附件和明细使用独立访问校验，记录正式结果查看/导出审计。
- [批量重算事务过大] → 先 dry-run 并按明确边界执行；若分批，保存批次状态和逐对象结果，排名发布在全部成功前保持阻塞。
- [SQLite 无法验证生产锁语义] → 在目标生产数据库验证唯一 current、版本 CAS、并发发布和回滚；未验证前不开放正式发布按钮。
- [契约已实现但界面仍不可用] → 将 mounted interaction tests、桌面/窄屏截图和真实浏览器旅程列为独立门槛，不接受构建或源码搜索替代。
- [新鲜环境缺少必需规则包或策略] → 启动准备幂等创建或明确失败，页面同时提供可定位的阻塞状态，避免空环境被误判为验收通过。

## Migration Plan

1. 增加角色化 DTO/契约测试以及派生字段写入防线，保持现有页面暂时可用。
2. 扩展规则包草稿 revision、来源关系、diff/validate/copy/publish 用例和迁移；从现有 2028 包演练复制 2029 草稿，但不自动发布。
3. 补齐排名 `correction_required`、幂等命令、阻塞项和角色查询契约；迁移现有批次时保留状态与审计。
4. 先完成并验收 `repair-2028-competition-workflow-acceptance`，确认竞赛权威上下文、新鲜环境准备和学生/教师浏览器闭环可用。
5. 先改管理员规则与排名页面，再改教师完整只读视图，最后改学生个人排名和统一计分展示；每步删除已替代的前端冗余字段与方法，并补齐产品级状态与 mounted component tests。
5. 将旧成绩管理页派生列改只读并接入重算 dry-run/execute；监控旧写端点调用并确认没有新工作流依赖。
6. 执行三角色端到端、隐私、并发、失败回滚、前端构建和生产数据库验证后启用新导航。
7. 回滚时关闭新页面 feature flag 并恢复旧只读入口；不可回滚覆盖已发布规则或排名，新增历史数据保留并通过后继版本纠正。

本 change 的退出条件是：竞赛新链路不再调用旧规则/成绩写接口，三个角色的权限旅程通过，2029 复制草稿可完成校验发布，排名从 draft 到正式发布及纠错可完整操作，且旧兼容入口被明确隔离和记录。

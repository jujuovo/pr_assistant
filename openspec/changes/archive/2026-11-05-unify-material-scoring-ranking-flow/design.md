# Design

## Context

参见 [proposal.md](proposal.md) 的动机。当前 `MaterialRecord` 已拥有结构化材料、附件、版本和事件，但明确不保存加分结果；`Application` 同时保存申报、审核和 `final_score`，`update_student_statistics()` 再把已通过申请汇总到 `Student`。审核路由在一次 HTTP 处理中直接匹配规则并提交申请，随后另行更新汇总，排名查询又把派生名次写回 `Student`，因此事务、数据所有权和失效边界不统一。

证书与志愿自动化已经依赖 `Application`，历史测试也验证这些路径。设计必须允许渐进接入和可对账迁移，不能通过一次性替换破坏现有审核记录。项目继续使用 Flask、SQLAlchemy、Vue 3 和现有数据库部署方式。

## Goals / Non-Goals

**Goals:**

- 建立材料事实、计分事实、学生试算快照和排名发布快照的单一所有权。
- 让审核、计分、汇总和试算排名失效在一个应用用例和事务中完成。
- 让单条审核、批量审核、自动化入口和未来管理命令复用相同用例，而不是复用 Blueprint。
- 在不重复入分的前提下兼容现有 `Application`、证书和志愿自动化数据。
- 提供稳定、可解释且包含状态和允许操作的 API 契约。
- 支持生产迁移前的历史对账、双读验证、切换和回滚。

**Non-Goals:**

- 不把 Flask 单体拆为微服务，也不新增消息队列作为前置条件。
- 不在本变更中全面改造视觉样式或所有角色页面布局。
- 不让 OCR 成为审核或计分的同步依赖。
- 不在兼容消费者和历史对账完成前删除 `Application` 或 `Student` 上的旧汇总字段。
- 不把所有旧数据自动认定为正确；无法解释的差异必须进入人工处理清单。

## Decisions

### 1. 采用模块化单体与单向依赖

后端按业务能力组织为材料、计分、排名和兼容适配模块，各模块内部区分 HTTP 适配、应用用例、领域规则和持久化。依赖方向为：

```text
HTTP / jobs / CLI adapters
            |
            v
Application use cases
            |
            v
Domain policies and state transitions
            |
            v
Repositories / ORM / files / OCR adapters
```

Blueprint 只解析请求、取得当前操作者、构造命令、调用用例并映射响应。用例不得读取 Flask `request` 或返回 `jsonify`；领域规则不得依赖 HTTP 或 Vue 字段名。

选择该方案是因为当前部署规模不需要跨服务一致性，数据库事务足以保护核心链路。备选的微服务会引入分布式事务、事件一致性和运维成本，暂不采用。仅按传统 `controllers/services/models` 搬文件也不足以明确业务所有权，因此不作为目标结构。

### 2. `MaterialRecord` 拥有材料与当前核验状态

`MaterialRecord` 继续保存学生、组织、类别、年度、结构化数据、分析结果、附件、当前状态和乐观锁版本；`MaterialEvent` 保存追加式操作历史。核验操作通过材料审核用例执行，状态机集中定义合法转换和 `allowed_actions`。

材料记录不保存权威总分。`verified` 只表示证据核验通过，是否产生分数由计分模块根据规则决定。审核事件保存结论、说明、操作者、材料数据摘要、附件摘要和版本；附件原件继续使用哈希校验和私有下载。

备选方案是继续让 `Application` 作为材料主记录，但其 JSON 附件、单组审核字段和两类粗粒度申请类型无法自然表达五类结构化材料及多次补正轨迹，因此仅保留为兼容来源。

### 3. 新增不可混淆的计分事实

引入概念上的 `ScoreEntry`，保存：学生、年度、分类、来源类型与来源标识、材料/审核引用、规则版本、原始分、系数结果、实际候选分、有效状态、失效原因、幂等键和时间。规则必须发布为不可变版本，或在计分时保存足以重放的规则快照。

分类封顶、最大计入数量和重复项选择不覆盖 `ScoreEntry` 的原始事实，而由汇总计算产生“实际计入/未计入及原因”。学生当前试算结果保存为可重建的 `StudentScoreSnapshot`，包含输入版本摘要、分类小计、综合分、规则版本集合和更新时间。`Student` 上的旧汇总字段在兼容期作为投影写入，不再作为新计分的输入来源。

使用 `(source_type, source_id, source_revision, rule_version)` 或等价唯一约束作为幂等键，保证审核重试和迁移重跑不会重复计分。

备选方案是继续直接更新 `Application.final_score` 和 `Student` 汇总字段；该方案无法稳定表达规则版本、冲销和排除原因，故不采用。

### 4. 一个审核用例拥有核心事务

`ReviewMaterial` 用例按以下顺序在单个数据库事务中执行：

```text
load record with version guard
  -> authorize actor and transition
  -> append review event
  -> create/invalidate score entries
  -> rebuild affected student score snapshot
  -> mark affected draft rankings stale
  -> commit once
```

任何同步步骤失败则整体回滚。审核命令携带材料版本和客户端幂等键；同一命令重试返回已有结果。单条审核、批量审核的每个原子单元、证书适配和志愿自动化必须调用统一计分用例，不直接修改汇总字段。

原件 OCR、通知和非关键分析不属于核心事务。它们使用已有任务/worker 机制在提交后执行；失败记录任务状态并允许重试，不反向改变核验事实。没有消息队列时，数据库任务记录是可恢复边界，不能依赖仅存在于进程内的回调。

### 5. 试算排名与正式排名采用不同生命周期

引入概念上的 `RankingBatch` 与 `RankingEntry`。批次保存年度、组织/专业范围、资格条件、截止时间、规则版本、精度、状态、输入摘要、创建/冻结/发布/撤回信息；条目保存学生、冻结分数、名次和稳定显示顺序。

状态机为：

```text
draft -> stale
  |        |
  +------> draft (regenerate)
  |
  v
frozen -> published -> withdrawn
  |
  +------> draft (unfreeze before publication)
```

任一相关 `StudentScoreSnapshot` 变化时，将未发布的相同范围批次标记 `stale`。正式发布必须重新校验输入摘要、迁移差异和参与资格。`published` 条目不跟随试算重算；纠错通过撤回旧版本并创建后继批次完成。

同分沿用现有竞赛排名 `1,1,3`。批次固定比较精度；同分组内按稳定、不影响名次的键排序，以保证重复生成展示顺序一致。

备选方案是实时查询并继续把 `major_ranking` 写在 `Student`，但它无法表达批次、发布时间、正式性和历史版本，因此仅作为兼容投影。

### 6. API 返回资源状态、解释与允许操作

新契约采用统一字段语义，不再依赖 `total_score || comprehensive_score` 等客户端回退。资源响应至少包含：

- 材料：`status`、`version`、`allowed_actions`、结构化数据、附件摘要和最近核验结论；
- 计分：规则版本、原始分、实际计入分、封顶/排除原因、有效状态和更新时间；
- 学生试算：基础成绩、分类小计、总分公式、输入版本和更新时间；
- 排名：批次、范围、`draft/stale/frozen/published/withdrawn`、版本、生成/发布时间和可见结果。

请求中的角色名、审核人和权威分数不得作为可信身份来源；操作者由认证上下文获得。前端可以依据 `allowed_actions` 展示操作，但后端仍重复执行全部权限和状态校验。

现有 API 在兼容期继续可用，由适配层读取新投影或调用新用例。新旧字段并存时响应明确标记 deprecated 字段和权威字段，避免双向同步。

### 7. 兼容适配采用单写新链路、受控投影旧字段

迁移切换后，所有新审核结果只通过统一用例写入 `ScoreEntry` 和快照，再由兼容投影更新必要的 `Application.final_score`、状态和 `Student` 汇总字段。禁止旧路由先写旧字段、再尝试补写新明细的双主模式。

历史 `Application` 使用来源适配器生成幂等的兼容 `ScoreEntry`。证书和志愿自动化保留自己的识别/批次模型，但最终认定通过统一计分端口。无法确定材料映射的历史申请使用 `legacy_application` 来源，不伪造 `MaterialRecord`。

读取迁移分三阶段：后台对账时双读比较；内部管理页面可显示差异；完成验收后新契约成为默认。旧消费者迁移完成前不删除旧字段。

## Risks / Trade-offs

- [新旧结果因历史 Bug 或规则语义不同而不一致] -> 保存逐学生、逐明细差异报告；差异未处理的范围禁止正式发布，不自动选择任一结果覆盖另一方。
- [审核事务重算范围过大造成锁竞争] -> 单次审核只重建一个学生快照并标记范围失效；全范围排名在独立显式用例中生成，不在审核事务内重排所有学生。
- [规则版本化增加数据量和管理复杂度] -> 规则版本不可变、通过引用复用；只在必要字段缺少稳定引用时保存快照。
- [兼容投影让旧字段暂时继续存在] -> 将其标记为只读投影，增加一致性测试和使用点清单，并设置明确退场门槛。
- [幂等键选择错误导致漏计或重复] -> 为人工审核、自动化批次和历史迁移分别定义稳定来源修订号，并在数据库增加唯一约束。
- [正式排名涉及隐私和行政风险] -> 默认只向学生暴露个人位置；完整名单、导出、发布和撤回均做组织授权与审计。
- [SQLite 与生产数据库事务/锁行为不同] -> 本地测试之外增加目标生产数据库的迁移、约束和并发验证，未验证前不宣称生产就绪。

## Migration Plan

1. 建立新表、约束和读取模型，但不改变现有生产写路径；在隔离数据库验证前向与回滚迁移。
2. 实现材料状态机、计分与排名用例及仓储，先以新测试验证规则、权限、回滚和幂等。
3. 编写历史 `Application` 只读扫描与 dry-run 对账工具，输出来源映射、缺失规则、重复项和汇总差异，不直接改数据。
4. 在备份和人工审核差异后执行可重复回填，生成兼容 `ScoreEntry` 与试算快照；保留回填批次和幂等键。
5. 将材料审核、证书和志愿自动化入口逐个切换为统一用例，并同步维护必要的旧字段投影；每切换一个入口即运行其现有回归测试。
6. 新 API 与前端消费者先双读比对，再切换为新契约；监控差异、权限拒绝和重算失败。
7. 启用排名批次的 draft/frozen/published 流程；只有迁移对账无阻塞项的范围允许首次正式发布。
8. 在所有旧消费者清单归零、连续对账一致且归档备份可用后，另立变更移除旧写路径和冗余字段。

回滚时停止新入口写入，保留新表和审计数据而不删除；在未发布阶段可把读取切回旧接口。若已经发布正式排名，则不得用技术回滚静默覆盖结果，必须按撤回/后继版本流程处理。数据库降级仅在确认没有新数据依赖且已备份后执行。

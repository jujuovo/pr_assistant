# Proposal

## Why

当前系统由 `Application` 承担旧申请、审核和最终分数，由 `MaterialRecord` 承担新材料及核验，两套状态与数据所有权重叠但没有统一的计分连接；成绩与排名又通过可被多处修改的汇总字段传播，容易产生“材料已核验但未入分”“分数已变化但排名仍陈旧”等不一致。现在需要先建立一条后端权威、可追溯且可渐进迁移的材料到排名业务链，作为后续前端工作流改造的稳定基础。

## What Changes

- 以 `MaterialRecord` 作为证明材料及其结构化申报、附件和核验事实的主模型，定义学生、教师和管理员可执行的状态转换与审计要求。
- 在材料核验与学生汇总之间引入独立、可追溯的计分明细；每条有效分数绑定材料、审核结论和规则版本，并支持分类封顶、撤销、补正和幂等重算。
- 将“审核材料并影响试算分”定义为后端统一用例与事务边界，避免前端或多个 Blueprint 串联核心写操作产生部分成功。
- 建立动态试算与正式排名发布的双层结果：试算可随有效输入重算，正式排名按年度/批次、范围和规则版本冻结为快照，发布后不得被静默改写。
- 为材料、计分、汇总和排名提供稳定的 API 契约及明确的 `allowed_actions`，前端只负责编排交互和展示，不自行维护权威业务规则。
- 采用渐进迁移：兼容现有 `Application`、证书与志愿自动化流程，通过明确适配路径接入统一计分；在完成数据核对和消费者迁移前不删除旧字段、旧表或旧接口。
- 保留原始材料、审核事件、规则版本、计分变更和排名发布记录，支持追溯、复核与撤销。
- 范围外：全面视觉重做、引入微服务或消息队列、扩展所有材料类别 OCR、立即删除 `Application`、一次性重写所有页面。

## Capabilities

### New Capabilities

- `material-evidence-review`: 管理证明材料的归属、附件、核验状态、角色权限、补正/撤回流程与不可丢失的审核轨迹。
- `auditable-scoring`: 根据已核验材料和固定规则版本生成可追溯计分明细，执行封顶、撤销、重算和学生试算分汇总，并保证核心操作的原子性和幂等性。
- `ranking-publication`: 按明确批次与范围生成动态试算和正式排名快照，定义同分排名、结果失效、冻结、发布和撤回行为。

### Modified Capabilities

无。当前项目尚无已建立的 OpenSpec durable specs。

## Impact

- 后端：`MaterialRecord`、`Application`、`Student`、规则与自动化相关模型；材料、申请和成绩 Blueprint；新增或重组的材料审核、计分与排名用例服务；数据库迁移和兼容适配。
- API：材料核验、计分解释、学生统计、排名试算与发布接口将获得稳定状态和响应契约；现有接口在兼容期内保留并标注权威来源。
- 前端：后续需让学生、教师和管理员页面消费统一状态、`allowed_actions`、计分明细和排名发布元数据；本变更不要求全面视觉重做。
- 数据：需要迁移清单、历史 `Application` 对账、规则版本绑定、派生汇总重建及旧排名失效策略；不得以静默覆盖方式改写正式历史结果。
- 测试：增加状态机、权限、事务回滚、幂等重算、分类封顶、兼容适配、排名批次与三角色关键旅程测试，并保留现有证书和志愿自动化回归。
- 依赖与部署：保持 Flask 模块化单体及现有 Vue 3 前端，不新增独立服务；生产数据库迁移需独立验证，不能以本地 SQLite 通过代替。

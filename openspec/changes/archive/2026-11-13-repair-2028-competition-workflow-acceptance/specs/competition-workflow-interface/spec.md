# Spec Delta

## Purpose

定义学业竞赛新链路在真实运行环境中的页面可用性、权威上下文加载、错误恢复和角色闭环，使学生与教师能够在不依赖隐藏配置或前端业务猜测的情况下完成申报、审核与反馈。

## ADDED Requirements

### Requirement: 竞赛入口只在权威上下文就绪时可操作
竞赛页面 MUST 从后端读取当前可申报周期、current 规则包、证据有效期和目录摘要；在上下文未加载、缺失或不一致时，系统不得呈现可提交的空表单或让客户端自行选择替代周期。

#### Scenario: 正式上下文加载成功
- **GIVEN** 当前用户有竞赛申报权限且后端存在可用的 current 规则包
- **WHEN** 用户打开竞赛申报页
- **THEN** 页面展示后端返回的周期、规则包版本和可搜索目录，并只按该上下文创建材料

#### Scenario: 当前规则包缺失
- **GIVEN** 当前申报周期没有可用的 current 竞赛规则包
- **WHEN** 用户打开竞赛申报页
- **THEN** 页面显示明确的配置阻塞原因和可恢复建议，禁用保存与提交且不以空目录冒充没有搜索结果

#### Scenario: 上下文加载期间
- **WHEN** 周期、规则包或目录请求仍在进行
- **THEN** 页面显示加载状态并阻止依赖未完成数据的操作，不展示可误操作的默认空选项

### Requirement: 竞赛申报页面提供产品级完整交互状态
学生页面 SHALL 使用项目现有设计系统组织目录搜索、材料事实、条件字段、附件、OCR/手填、状态历史和计分反馈，并在支持的桌面与窄屏视口保持字段标签、控件、按钮和说明可读可操作。

#### Scenario: 学生填写普通竞赛材料
- **GIVEN** 权威竞赛上下文加载完成
- **WHEN** 学生搜索目录、选择竞赛并填写后端 field schema 要求的字段
- **THEN** 页面以分组表单展示只读分类和条件字段，明确必填项、验证结果与下一步操作

#### Scenario: 条件字段随目录变化
- **WHEN** 学生从个人项目切换到需要团队排序或专项赛制的目录项
- **THEN** 页面只显示当前 field schema 所需字段，清除不再适用的旧值并说明验证错误

#### Scenario: 窄屏访问
- **WHEN** 用户在支持的窄屏视口打开竞赛申报或审核页
- **THEN** 标签、输入框、状态说明和主要操作按可读顺序换行，不发生控件相互覆盖或横向挤压导致不可操作

### Requirement: 读取与写入状态可区分且可恢复
页面 MUST 分别呈现首次加载、空记录、搜索无结果、配置阻塞、字段验证、网络失败、权限拒绝、版本冲突、写入进行中、成功和可重试失败；失败不得清除用户仍有权保留的确认输入。

#### Scenario: 搜索没有匹配项目
- **GIVEN** current 目录已经成功加载
- **WHEN** 搜索词在正式目录中没有匹配项
- **THEN** 页面显示“正式目录无匹配结果”空状态并允许修改搜索词，不把它描述为规则包缺失或网络失败

#### Scenario: 保存草稿网络失败
- **WHEN** 学生保存合法草稿但请求因网络或服务错误失败
- **THEN** 页面保留已填写事实、显示可重试错误和失败操作，不宣称保存成功

#### Scenario: 版本冲突
- **WHEN** 客户端基于旧材料版本执行上传、提交、补正或重新确认
- **THEN** 页面显示版本冲突，读取最新权威状态并要求用户重新确认，不以旧输入覆盖新版本

### Requirement: 后端错误保持稳定语义和可操作说明
客户端 SHALL 优先依据后端稳定 error code 映射用户说明，并在未知 code 时保留安全的后端错误语义或请求标识；不同根因不得统一映射为“核对材料”。

#### Scenario: 配置缺失错误
- **WHEN** 后端返回当前规则包缺失的稳定 code
- **THEN** 页面说明该问题需要管理员准备规则包，学生材料内容不是失败原因

#### Scenario: 附件缺失错误
- **WHEN** 后端返回 `competition_attachment_required`
- **THEN** 页面定位到附件步骤并提示先上传证明原件

#### Scenario: 未知服务错误
- **WHEN** 后端返回客户端未识别的错误 code
- **THEN** 页面显示不会误导用户修改业务事实的通用服务错误，并保留可用于排查的安全标识

### Requirement: 每个用户动作只触发一个权威命令
页面 MUST 为目录选择、保存、上传、OCR 控制、提交、补正、放弃和重新确认建立单一请求责任；父子组件挂载或按钮重复点击不得产生重复写命令，读取刷新也不得互相覆盖新状态。

#### Scenario: 页面首次挂载
- **WHEN** 学生直接打开竞赛材料页
- **THEN** 系统按明确依赖顺序加载一次上下文和必要记录，不由父子组件重复请求同一资源

#### Scenario: 重复点击保存
- **WHEN** 学生在保存请求完成前再次点击保存
- **THEN** 页面合并或阻止重复命令并保持同一幂等语义，不创建重复材料

#### Scenario: OCR 迟到后刷新
- **GIVEN** 学生已停止 OCR 并确认手填值
- **WHEN** 旧任务迟到返回且页面刷新记录
- **THEN** 页面继续展示学生确认值和迟到隔离状态，不用 OCR 原文覆盖表单

### Requirement: 竞赛闭环必须在真实浏览器中可完成
受支持浏览器中的实际页面 SHALL 能从 fresh local database 完成学生目录选择与草稿、附件和 OCR/手填、提交、教师只读审核、后端计分及学生反馈；每一步必须展示与后端权威状态一致的结果。

#### Scenario: fresh database 完整旅程
- **GIVEN** 使用项目正式本地准备命令创建全新数据库并启动前后端
- **WHEN** 学生提交合法竞赛材料、教师通过、学生读取反馈
- **THEN** 目录请求成功、页面全程可操作，最终材料状态、计分明细、快照和反馈一致且没有旧 `Application` 竞赛来源

#### Scenario: fresh database 依赖未准备
- **GIVEN** 本地准备无法提供正式规则包或周期依赖
- **WHEN** 启动命令结束或用户打开竞赛入口
- **THEN** 准备命令失败或页面明确保持功能关闭，不得报告环境已准备且同时返回不可解释的 404

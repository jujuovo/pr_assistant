# Design

## Context

参见 [proposal.md](proposal.md)。当前证书预览把 `student_values[*].date` 与外围表单 `awardDate` 独立提交，后端直接用后者写 `Application.award_date`，没有一致性检查。规则确认又要求客户端提交 `rule_id`，而权威匹配只考虑周期、材料类别和学院，无法区分竞赛名称、等级、赛区和组别，因而既可能漏配，也可能让三等奖误用泛化 5 分规则。

现有 change 已建立周期政策、规则版本、统一审核计分、`ScoreEntry`、`StudentScoreSnapshot` 和排名门禁。本次修订保留这些成果，但把规则覆盖检查从教师审核阶段前移到学生正式提交前，并将结构化材料事实归还给材料模型管理。

## Goals / Non-Goals

**Goals:**

- 建立学生确认结构化证据的唯一权威快照，并从中形成规范化 `award_date`。
- 建立可填写、可发布、不可变且不会歧义匹配的结构化计分规则。
- 让无规则材料只停留在学生与管理员责任范围，不进入教师端。
- 让规则补齐后必须经学生重新确认才能提交。
- 让错误日期通过新版本补正和重新审核，保留旧审计链。
- 继续保证审核、计分、快照、兼容投影和排名失效的事务一致性。

**Non-Goals:**

- 不让 OCR 自动确认事实、选择规则、核验材料或计分。
- 不引入基于自然语言或模糊相似度的权威规则匹配。
- 不让管理员替学生确认材料，也不让规则发布自动提交或计分。
- 不重写排名算法，不删除旧表和兼容字段，不引入微服务或消息队列。

## Decisions

### 1. 学生确认的结构化材料快照是规则与日期的唯一输入

为每个材料版本保存逻辑上的 `confirmed_terms` 快照，至少覆盖材料类别、竞赛名称、奖项等级、竞赛级别/赛区、组别、赛道和证据日期。字段同时保留：

- `ocr_raw_terms`：OCR 原始输出，仅作来源证据；
- `student_confirmed_terms`：学生确认或修正后的原始表达；
- `normalized_terms`：后端按受控词表和日期解析规则生成的匹配输入。

`award_date` 只从当前版本的确认日期规范化形成。兼容页面仍提供独立申请日期时，后端比较二者；规范化后不一致返回 `award_date_confirmation_conflict`，不写入任一候选值。备选方案“优先 OCR”会把识别误差变成权威事实；“优先表单”正是当前故障来源，均不采用。

### 2. 规则采用不可变条件快照而非客户端选择 `rule_id`

管理员规则填写模块编辑草稿规则，发布服务生成不可变 `RuleVersion`。规则版本快照包含：周期、学院范围、材料类别、竞赛名称、奖项等级、竞赛级别/赛区、组别/赛道、分值、上限、次数及摘要。维度使用显式值或显式通配语义；缺失字段不等于匹配全部。

客户端可以展示匹配结果，但不能以提交 `rule_id` 决定权威规则。后端根据材料快照计算匹配并在正式提交时固定 `rule_version_id`。修改已发布规则产生新版本，既有提交继续引用原版本。

### 3. 匹配是精确、可解释且必须唯一的

匹配器先按固定周期、学院范围和材料类别筛选，再逐个比较规范化竞赛词条。每个候选返回命中条件和未命中维度。结果只有三种：

```text
matched(rule_version_id, score explanation)
unmapped(material_terms_unmapped, missing dimensions)
ambiguous(ambiguous_scoring_rules, conflicting versions)
```

不采用查询顺序、最高分、最近版本或仅类别匹配作为消歧策略。发布前使用同一匹配语义检测规则条件交集；若存在能同时命中两条规则的合法词条，拒绝发布。这样三等奖不会命中一等奖或泛化 `competition` 规则。

### 4. 提交前状态机隔离无规则材料

材料主状态转换为：

```text
draft
  -> rule_unmatched       保存成功但没有唯一规则
  -> rule_available       后来已有唯一规则，等待学生确认
  -> submitted            学生确认当前材料版本、规则版本和候选分
  -> under_review         教师开始核验
  -> needs_correction     教师要求补正，学生创建新版本
  -> verified_not_eligible
  -> scored
```

`rule_unmatched` 只允许学生查看/编辑和管理员查看聚合词条；`rule_available` 允许学生查看匹配规则、修改、确认或放弃。二者不属于教师待审核查询范围，直接审核命令也必须拒绝。`submitted` 必须同时固定材料版本、周期政策版本和规则版本。

选择保存无规则材料而非拒绝保存，是为了保留学生证据并让管理员看见规则缺口；选择学生重新确认而非规则发布自动提交，是为了避免规则变化静默改变学生申报意图。

### 5. 规则发布只同步覆盖状态，不产生业务终态

规则发布事务完成后，后台可同步或幂等异步扫描与规则范围相关的 `rule_unmatched` 材料。只有重新匹配为唯一结果的对象转换为 `rule_available`；仍无匹配或歧义的对象保持原状态并更新原因。该过程不得：

- 创建教师审核任务；
- 写核验结论；
- 创建或修改 `ScoreEntry`；
- 创建 `StudentScoreSnapshot`；
- 更新旧最终分投影。

扫描采用规则版本和材料版本组成幂等键，失败可重试。通知学生属于可异步副作用，不影响状态事务提交。

### 6. 教师用例只处理已固定规则的正式提交

教师审核入口先验证材料状态为 `submitted/under_review`、来源版本未变化、固定规则版本仍可读取且操作者具有组织范围权限。教师只判断真实性、拒绝或要求补正；通过时使用提交时固定的规则版本计算自动分。

核心事务顺序为：

```text
lock submitted material version
  -> authorize reviewer
  -> validate fixed cycle and fixed rule version
  -> evaluate normalized award_date eligibility
  -> calculate automatic score
  -> authorize optional override
  -> append review and override audit
  -> create/invalidate ScoreEntry
  -> rebuild StudentScoreSnapshot
  -> mark matching draft RankingBatch stale
  -> update legacy projections
  -> persist idempotency result
  -> commit once
```

快照、审计、投影或排名失效失败整体回滚。理论上不应再在教师审核阶段出现正常的 `needs_rule`；若历史或损坏数据缺少固定版本，返回数据完整性阻塞并进入管理员修复，而不是把责任交给教师。

### 7. 日期错误通过版本化补正恢复

已提交或已核验材料不得原地修改日期。发现日期录入错误时，创建补正请求并允许学生从旧版本派生新草稿：保留附件引用和 OCR 来源，要求学生重新确认结构化字段。新版本继承固定周期但重新执行日期一致性与规则匹配；学生重新提交后产生新的审核命令。

旧版本的 `verified_not_eligible`、教师核验和资格原因保留。新审核成功时，统一计分用例使同来源旧有效计分失效并重建快照，避免重复累计。禁止直接修改数据库日期后补写分数。

### 8. 三个角色读取不同投影但共享后端权限

- 学生“我的项目”合并材料状态与权威计分解释。`rule_unmatched` 显示展示分 0、未审核和固定提示；该 0 不映射为 `ScoreEntry`。若没有任何有效明细，返回“尚无权威计分快照”而非旧字段总分。
- 教师列表只查询已正式提交且固定唯一规则版本的材料；前端隐藏不是安全边界，直接接口同样拒绝其他状态。
- 管理员规则模块提供草稿编辑、发布预检、冲突解释和未覆盖词条聚合。聚合默认不返回学生身份或附件；管理员不能替学生确认或提交。

API 以稳定状态、原因码和 `allowed_actions` 驱动界面，不由页面自行推断权限。

### 9. 渐进迁移保留 Application 兼容投影

新增结构采用非破坏迁移。`MaterialRecord` 及版本事件逐步成为结构化证据权威来源，`Application` 暂时保留列表与旧接口投影。迁移 dry-run 分类：日期来源冲突、缺少确认快照、无规则、规则歧义、已审核无明细和快照缺失。

自动迁移只能处理有明确确认证据的对象；本次已发现的错误日期材料必须进入学生补正，不得由脚本猜测 OCR 日期即为学生确认日期。旧消费者归零且连续对账一致后，才在独立 change 删除投影。

## Risks / Trade-offs

- [结构化维度过严导致更多未匹配] → 管理员未覆盖词条聚合和发布预检让缺口可见，禁止用错误默认分换取表面命中率。
- [规范化词表变化影响匹配] → 规范化策略版本化，提交保存输入与结果快照，历史不随词表更新漂移。
- [规则发布扫描大量草稿] → 按周期、学院、类别缩小范围，使用幂等批次；扫描失败不回滚已发布规则，也不产生审核或计分。
- [兼容 Application 与材料状态暂时重复] → 明确 MaterialRecord 为新流程事实来源，Application 只作投影并持续对账。
- [学生看到 0 误以为已计分] → DTO 同时返回 `verification_status = unreviewed`、`scoring_status = rule_unmatched` 和固定说明，禁止生成零分 `ScoreEntry`。
- [SQLite 无法证明发布扫描和审核锁语义] → SQLite 覆盖行为，目标 PostgreSQL 验证唯一约束、行锁、并发发布与审核。

## Migration Plan

1. 增加结构化确认快照、规范化版本、固定规则版本和新材料状态所需的非破坏性字段/表及索引，保留旧数据与投影。
2. 部署只读 dry-run，报告日期冲突、缺少确认快照、未覆盖词条、歧义规则和受影响排名范围；完成备份和业务确认。
3. 上线规则草稿、发布预检、不可变版本和管理员未覆盖词条 API；先迁移演示规则为完整结构化条件。
4. 上线学生确认、日期冲突门禁、提交前匹配和 `rule_unmatched/rule_available` 状态；教师查询同步收紧。
5. 上线版本化日期补正、学生重新提交和统一审核计分适配；对已知错误对象只通过补正恢复。
6. 更新学生、教师、管理员界面和操作文档，运行端到端、权限、回归和生产构建验证。
7. 在隔离 SQLite 与目标 PostgreSQL 执行升级、回滚、规则发布扫描、并发提交/审核和对账演练；差异未清零时禁止正式排名发布与 change 归档。

应用回滚可恢复旧读取，但不得删除已保存的结构化快照、规则版本和审计事件。数据库降级只在确认没有新数据依赖且备份可恢复时执行。

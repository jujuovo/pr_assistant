# Design

## Context

参见 `proposal.md` 的动机与范围。当前仓库已存在 `MaterialRecord`、`RuleVersion`、`ScoreEntry`、材料状态机和周期快照，但竞赛路径仍同时依赖可变 `Rule`、旧 `Application`、客户端 `rule_id`/估分及通用 `max_count` 聚合。`ApplicationForm.vue` 承担旧规则选择和本地业务判断，而 `MaterialWorkflow.vue` 只暴露最小状态操作，尚不能承载完整竞赛申报与反馈。

附件 2 及正文是本次规则数据的权威证据；PDF 内容不能直接在运行时驱动计算，必须转录为可校验、可版本化的正式规则包。现有数据库仅含测试数据，允许清空重建，但其他材料类别仍依赖旧模型，因此只能对竞赛切流，不能立即删除旧表和接口。

## Goals / Non-Goals

**Goals:**

- 在模块化单体内形成竞赛目录、材料事实、审核结论、自动计分、专项聚合与学生反馈的单向依赖。
- 让一个后端用例拥有审核通过到快照更新的事务边界，并提供版本并发控制和幂等重试。
- 将 2028 规则包作为经测试的不可变正式数据装载，完整覆盖特殊条款并能解释所有排除决定。
- 建立其他材料类别今后迁移到 `MaterialRecord + RuleVersion + ScoreEntry` 可复用的模式。

**Non-Goals:**

- 不实现 2029 规则复制、差异编辑与发布 UI。
- 不迁移非竞赛类别，不物理删除 `Application`、`Rule`、`RuleCalculation` 或旧 `/rules`。
- 不改变正式排名的生成、冻结、解冻与发布职责；本次只使现有 draft 排名按分数变化失效。
- 不使用 OCR 判断真实性、团队排序证明力或审核结论。

## Decisions

### 1. 使用“规则包 + 原子目录 + 政策快照”，而非继续扩张单条 `Rule`

为周期建立一个当前 `CompetitionRulePackage` 概念（可由新表或明确的聚合根实现），包含版本、状态、内容摘要、有效期、原子竞赛目录和政策配置。每个目录项拥有稳定 `competition_id`、正式名称、别名仅用于搜索、分类、赛事族、合法级别/奖项/赛制以及所需字段模式。发布后内容不可变；`RuleVersion`/计分明细保存包版本与实际命中政策快照。

规则数据以仓库内受版本控制的声明式种子文件保存，加载前执行 schema、唯一标识、目录拆分、合法组合、矩阵覆盖、专项规则引用和重叠校验。正式分值和团队系数必须逐条对照 PDF 建立测试夹具，不从前端常量推导。

替代方案是为每个组合继续创建可变 `Rule` 行；这会让目录、专项互斥和规则包原子发布割裂，也难以保证同周期唯一版本，因此不采用。

### 2. 竞赛材料以 `MaterialRecord` 为唯一事实，旧 `Application` 仅服务未迁移类别

竞赛创建 API 接受目录标识、学生确认字段和附件引用，不接受规则编号或分数。规范化快照至少包含 `competition_id`、`project_name`、`award_date`、实际级别、奖项、年份/届次，以及按目录要求出现的团队总人数、本人排序、CSP 百分位、ICPC/CCPC 赛制等。名称基础规范化只处理空白、大小写和全半角等确定变化，不做模糊合并。

精确重复由学生、周期、目录项和规范化关键词条摘要的唯一性/用例校验阻止。同作品分组键来自规范化 `project_name`；同赛事键来自规则包的赛事族、年份和正式互斥维度。轻微改名不做猜测性自动合并，由教师汇总表发现并退回学生修正。

兼容隔离通过类别路由完成：`competition` 只进入新用例且不得生成旧计分来源，其他类别继续旧链路。退出条件是所有类别迁移且对账完成后，再由后续 change 删除旧模型。

### 3. OCR 是可取消的异步辅助任务，学生确认快照拥有权威性

OCR 任务记录 `job_id`、材料版本、状态和取消/废弃标志。学生选择手填时同步把当前任务标为 cancelled/ignored 并提升材料版本；工作线程回写前必须比较任务状态和材料版本。迟到结果可作为诊断审计保存，但不得回写 `confirmed_terms`。

附件保存和材料草稿是同步核心操作；OCR 调度可在提交后异步重试。OCR 服务不可用不得阻止学生手填。替代方案是等待工作线程真正终止后才允许手填，但无法可靠中断外部识别且损害交互，因此采用逻辑取消与 CAS 防迟到写入。

### 4. 审核用例只接受 `approve`/`return`，通过时同步执行完整计分

教师命令契约包含材料版本、动作、意见和 `idempotency_key`。读取上下文可展示后端计算的候选分，但写命令 schema 明确拒绝改材料、选规则和改分字段。

`return` 在单事务中写审核命令、状态、意见与事件，不生成有效分。`approve` 在一个数据库事务中依次锁定材料与学生、校验版本/权限/固定规则包、写审核事实、计算个人分、写/替换 `ScoreEntry`、重新分配该生全部竞赛明细、重建周期快照、标记 draft 排名失效并写审计。任何异常整体回滚。幂等键绑定操作者、材料版本、动作与规范化载荷；相同键同内容重放原结果，不同内容返回冲突。

通知不属于核心事务。规则更正或退回产生 outbox/可重试通知意图，发送失败不回滚权威状态。

### 5. 竞赛专项聚合使用分阶段、确定性的纯政策管线

计分先由目录分类、级别、奖项和团队分配得到个人候选分，再按固定顺序执行：无效/精确重复防线 → CSP 最高项 → 同年 ICPC/CCPC 最高项 → 同赛事最高项 → 同作品最高项 → 剩余候选最高三项 → 学业专长 15 分封顶。每阶段只消费上一阶段仍符合资格的候选项，并给被排除项写稳定 reason code。

分数降序后的同分决胜使用规则包声明顺序、证据日期和稳定材料标识，确保重算一致。所有候选仍保留在 `ScoreEntry` 或等价投影中，`included` 与 `exclusion_reason` 可重建，不删除低分材料。通用 `allocate_candidates(max_count)` 可保留给其他类别，但竞赛调用专用政策对象，避免把特殊条款塞入页面或 Blueprint。

### 6. 规则更正采用“失效并重新确认”，禁止静默重算

新包启用前生成影响预览，将旧/新包对每条受影响材料的匹配和候选分进行比较。启用事务保留旧包只读快照，将受影响材料标记为 `rule_reconfirmation_required`（或现有状态机中的等价显式状态），可审计失效其当前分并重建快照，同时创建学生通知意图。学生确认新快照后产生新材料版本并重新提交，教师重新审核后才生成新分。

未受影响且尚未提交的草稿改用新包；已绑定历史版本始终可展示旧依据。规则更正不直接操作正式发布排名；若未来存在冻结结果，由下一 change 的管理员解冻流程处理。

### 7. API 以服务端字段模式驱动最小可用前端

新增/扩展只读契约：当前竞赛规则包摘要、可搜索目录、选中项目的合法选项与 required-fields；材料详情同时返回 OCR 原文、confirmed terms、固定规则依据、候选分、审核历史和 allowed actions；学生分数端返回每项 candidate/effective/included/reason 与竞赛合计；教师端返回授权学生汇总及只读审核上下文。

前端根据服务端 field schema 渲染选项和条件字段，不保留独立分值表。竞赛入口改接新材料 API；旧表单继续服务未迁移类别。错误码如 `duplicate_submission`、`version_conflict`、`rule_package_changed` 和各排除码由统一展示映射转换为用户语言，但不得改变业务判断。

## Risks / Trade-offs

- [PDF 为扫描件，转录条目或团队系数可能出错] → 建立逐条来源注释、双人核对清单、目录数量/摘要测试和规则黄金用例；未核对条目不得标记正式。
- [规则更正立即失效旧分会使学生总分暂时下降] → 明确显示“待重新确认”，保留旧历史值及原因，并可靠通知；不以旧分继续冒充当前有效结果。
- [按学生填写项目名分组可被轻微改名绕过] → 保持确定性自动规则，提供教师全量汇总核对和退回修正；避免不可解释的模糊算法误伤。
- [每次审核重算该生全部竞赛明细增加事务成本] → 只锁定单个学生和周期、建立查询索引；竞赛条目规模有限，优先保证一致性，性能测试后再优化。
- [竞赛新旧路径并存导致双计分] → 类别级唯一写入口、来源唯一约束、对账测试和监控；在退出条件满足前保留旧表但禁止竞赛写入。
- [SQLite 测试无法证明生产数据库锁与约束语义] → 补充目标生产数据库的迁移、唯一约束、并发和回滚验证，未验证前不得宣称可生产发布。

## Migration Plan

1. 完成规则包 schema、正式 2028 数据和只读校验命令；用黄金测试确认 PDF 全部竞赛条目和特殊计分条款。
2. 增加所需表/字段、状态、索引与约束；因现存数据仅为测试数据，备份后清空并从空库迁移，随后装载唯一 2028 正式包。
3. 先部署后端目录、材料、OCR 控制、审核计分和反馈契约，在 feature flag/类别路由下仅对 `competition` 开启。
4. 部署学生和教师最小闭环 UI，确认不再向竞赛接口发送旧权威字段；其他类别保持旧入口。
5. 执行三角色旅程、并发/失败回滚、规则更正、分数对账、前端构建及目标生产数据库验证后开启竞赛新路径。
6. 回滚时关闭竞赛新入口并恢复迁移前测试库备份/回退 schema；已生成的新链路审计数据应导出保留，不将其反投影为旧 `Application` 正式分。

退出兼容期的条件是：竞赛新路径连续通过对账、其他类别均完成同类迁移、没有旧来源有效分，且后续独立 change 已提供旧模型删除迁移与回滚方案。

# 第一部分 · 已有代码总结

## 1.1 系统定位

**GradPush —— 推免（保研）加分申报与审核平台。** 把线下的纸质申报与人工核算搬到线上：学生在线提交加分申请，教师在线审核，管理员配置规则、管理成绩、出统计报表。

## 1.2 技术栈

| 层 | 选型 |
|---|---|
| 前端框架 | Vue 3.5 + Vue Router 4.5 + Pinia 3.0 |
| 构建 | Vite 7 |
| 前端库 | Font Awesome（图标）、xlsx（前端导出 Excel） |
| 后端 | Python + Flask 3.1 |
| 数据层 | SQLAlchemy 2.0 + Flask-SQLAlchemy；默认 PostgreSQL，可切 SQLite |
| 数据库迁移 | Flask-Migrate（Alembic） |
| 会话 / 缓存 | Flask-Session、Flask-Caching |
| 安全 | bcrypt 密码哈希、图形验证码（绑定 IP + User-Agent） |
| 其他 | openpyxl / python-docx（导入导出）、pytz（时区处理） |
| 测试 | pytest + coverage + flake8 |

## 1.4 系统架构

前后端分离。前端是单页应用，通过 HTTP 调用后端 REST 接口。

**前端**

只有 4 个路由页：登录、学生、教师、管理员。前端路由带**角色守卫**——登录身份与目标页面不匹配，直接踢回登录页。

三个工作台结构一致：「顶部信息栏 + 可折叠侧栏 + 内容区」。功能页按角色分目录放在 `components/student`、`components/teacher`、`components/admin` 下。

状态管理用 Pinia，4 个 store：`auth`（登录态）、`applications`（申请数据）、`files`、`toast`（消息提示）。

**后端**

按业务域切成 9 个 blueprint：

|---|---|---|
| admin_bp | 21 | 学院/系/专业增删改、系统设置、学院分数设置、推免文件 |
| rule_bp | 13 | 规则增删改、规则算式、规则匹配与计算、启停 |
| user_bp | 13 | 用户查询与管理、批量导入、改密、头像 |
| auth_bp | 12 | 验证码、登录、注册、密码重置、组织架构查询 |
| system_bp | 10 | 备份/恢复、日志查看下载、缓存清理 |
| application_bp | 7 | 申请增删改查、审核、待审核列表 |
| score_bp | 5 | 综合成绩重算、排名、统计 |
| organization_bp | 5 | 组织架构查询与导入 |
| public_bp | 1 | 系统信息 |

## 1.5 数据模型（11 张表）

**组织架构（3 张）**：`Faculty` 学院 → `Department` 系 → `Major` 专业，三级级联。

**用户（2 张）**

- `User` —— 账号、bcrypt 密码哈希、角色（student / teacher / admin）、学院系专业外键、状态（active / disabled）。保存前后与 Student 双向同步。
- `Student` —— 学号、姓名、CET4 / CET6 成绩、推免绩点 `gpa`、换算后的学业成绩 `academic_score`、学术专长总分、综合表现总分、**综合成绩** `comprehensive_score`、**专业排名** `major_ranking` 与排名人数。

**申请（1 张）**

- `Application` —— 项目名、获奖日期、类型（`academic` 学术专长 / `comprehensive` 综合表现）、**自评分** `self_score`、状态（pending / approved / rejected / **draft**）、附件 JSON `files`、动态系数 JSON `dynamic_coefficients`、关联规则；审核侧有核定分 `final_score`、审核意见、审核时间、审核人。

**规则（3 张）**

- `Rule` —— 规则名、类型、子类型（科研成果 / 学业竞赛 / 创新创业训练等）、基础分 `score`、`max_score` 最大分、`max_count` 最大项目数、状态、所属学院、`calculation_formula`。
- `RuleCalculation` —— **与 Rule 一对一**。计算方式（fixed 固定分 / ratio 比例 / formula 公式）、`formula` **公式字符串**、`parameters` 参数 JSON、最大分、精度。
- `FacultyScoreSettings` —— 每个学院一套权重：学业成绩占比（默认 80%）、学术专长上限（默认 15）、综合表现上限（默认 5）。

**系统（3 张）**

- `Captcha` 验证码（token、文本、用户标识、过期时间）
- `SystemSettings` 系统设置（学年、**申请起止时间**、单文件与总文件大小限制、在线 / 维护状态）
- `GraduateFile` 推免相关文件（按学院归属）

## 1.6 几个值得注意的设计

**① 计算引擎是这个系统最值钱的部分。** 「规则 → 计算方式 → 系数 → 分数」这条链路是完整跑通的，而且支持按学院配置权重。这是后续所有改进的底座。

**② 但规则的计算公式是「字符串」。** `RuleCalculation.formula` 存的是形如 `base_score * level_factor * grade_factor` 的文本，参数放在 JSON 里。灵活，代价是**必须由管理员手工编写**——这就是「用户没有耐心从零建规则」的技术根源。

**③ 已经有时序概念，但没有提醒。** `SystemSettings` 里有 `application_start` / `application_end`，说明系统知道申报有窗口期——但窗口期只体现在「能不能提交」，**没有任何对学生的提醒机制**。

**④ 申请状态里有 `draft`。** 说明设计时考虑过「填一半先存」。

**⑤ 安全这部分做得不错。** 密码 bcrypt 哈希、登录有图形验证码、会话用 Flask-Session、有备份恢复和日志查看。作为一个课程项目，完成度是够的。

| 方法 | 对象 | 规模 | 性质 |

| 问卷 | 在校学生 | **45 份有效**（测谎题 45/45 通过） | 定量，主体证据 |
| 线上访谈 | 辅导员 | **1 人** | 定性，探索性 |
| 线上访谈 | 学生会学长 | **1 人** | 定性，探索性 |
| 代码走查 | GradPush 源码 | 约 2.8 万行 | —— |
| 文档分析 | 原项目 `Problems.md` 等 | —— | —— |

**访谈的定位要说清楚**：两次访谈各只有 1 人，属于**探索性访谈**，用途是**发现问题、形成假设**，不提供统计结论。

它们真正的价值在于：两人独立提到的点，恰好和学生问卷里排前两位的诉求方向一致。**方向一致增强了我们的判断，但这不构成定量证据。**

## 2.1 计算与规则类

| 问题 | 证据来源 | 改进方法 |
|---|---|---|
| 快一半的人不知道怎么算分 | 问卷：46.67% 选「有计算需求，但还不知道如何计算」 | 把规则通俗化——选规则时用人话讲清"这条要求什么、能加多少" |
| 规则必须从零手工建 | 原项目文档原话："用户是没有耐心从零添加规则的"；代码：`formula` 是手工写的字符串 | 预置常见规则模板，管理员**基于模板改**而不是从零写 |
| 最大项目数 / 最大分数限制没真正生效 | 原项目文档："相关的实现没有实际应用" | 把 `max_score` / `max_count` 落到计算逻辑里 |
| 超额申报被硬性拦截 | 原项目文档 | 允许超额申报，系统**自动取最高分前 N 项** |
| 四六级、绩点换算方式不对 | **辅导员**：要"正确识别加分材料"；原项目文档："需要上传材料然后老师进行编辑修改，而不是管理员独立设置" | 改成**学生上传材料 → 教师审核确认/修改** |
| 志愿时长靠学生自己算 | 原项目文档；学生会：要"输入保研条例自动换算成绩" | 改成管理员配算式，**学生只填总时长**，系统自动算；并支持多次申报累计 |

## 2.2 信息与预期类

| 问题 | 证据来源 | 改进方法 |
|---|---|---|
| 不清楚申报流程、材料要求、时间节点 | 问卷：**71.11%**（最高频困惑） | 做**保研流程与时间线展示**（学生会也明确提了这一条） |
| 参加完活动才发现不符合加分条件 | 问卷：**48.89%** | 做**事前判断**：填一项经历，系统当场告诉用户符不符合 |
| 不同人对同一条规定解释不一致 | 问卷：51.11% | 规则文本结构化 + 统一解释入口 |
| 材料找不到、不全、格式不符导致重复提交 | 问卷：42.22% | 做**材料集中管理**：证书成绩单统一归档，申报时直接取 |
| 错过通知或截止时间 | 问卷：31.11% | 做**截止时间与政策更新提醒** |
| 自己算的分与最终认定不一致 | 问卷：22.22% | 计算口径统一、结果可追溯 |
| 看不到历年保研情况 | **学生会**：要展示历年保研比例、保研去向 | 新增**历年信息**模块 |

## 2.3 呈现与操作类

| 问题 | 证据来源 | 改进方法 |
|---|---|---|
| 统计报表只显示审核通过的项目 | 原项目文档 | 显示**全部**（含未通过），否则学生不知道为何没加上分 |
| 报表不显示动态系数、不显示志愿总时长 | 原项目文档 | 报表补上这两个维度 |
| 报表不能排序 | 原项目文档 | 表头与内容支持按项排序 |
| 审核弹窗没有分页，审完一条要关掉再开 | 原项目文档 | **加分页 + 审完自动跳下一条** |
| 管理员编辑用户时账号改不了 | 原项目文档（小 bug） | 直接修 |
| 学生无法删除自己未通过的申请 | 原项目文档 | 允许删除（或归档） |

> **注意**：2.3 这类问题**调研里没有印证**——学生问卷覆盖不到教师端。它们全部来自原项目文档和代码走查。这也是把它们的优先级排在后面的原因之一。

# 第三部分 · 流程与路线规划

## 3.1 现有流程

**登录与分流**：账号密码 + 图形验证码 → 判定角色 → 进入对应工作台。三个工作台入口分开，前端有角色守卫。

**学生**（这是核心流程）
1. **加分申请** —— 四段式表单：基本信息（项目全称 + 获得时间）→ 规则选择（下拉显示规则名与基础分，选中后展示规则说明）→ **规则系数填写**（按所选规则**动态生成**输入项，边填边实时算预估分）→ 材料上传与自评说明。提交后进入审核队列。
2. **申请记录** —— 查看已提交申请的状态，可再编辑。
3. **加分统计** —— 自己的加分汇总。
4. **个人信息**。

**教师**：待审核申请（待办列表）→ 逐条核对 → 通过 / 驳回 → 审核记录留档 → 统计报表。

**管理员**：学院管理（三级组织架构）、用户管理（增删改 / 批量导入 / 重置密码）、规则管理（规则 + 算式 + 启停）、成绩管理（重算综合成绩 / 排名 / 统计）、申请管理、推免文件管理、统计报表、系统设置（备份恢复 / 日志 / 缓存 / 按学院配权重）。

**端到端主线**

```
管理员：搭组织架构 → 配规则和算式
   ↓
学生：选规则 → 填系数 → 传材料 → 提交申请
   ↓
教师：逐条审核 → 通过 / 驳回
   ↓
管理员：按规则汇总 → 算综合成绩 → 排名与报表 → 公示
```

## 3.2 核心判断

学生问卷是定量主体，两次访谈是定性补充。三者放在一起看，方向相当集中：

- 学生会学长提的第一个需求是「输入保研条例自动换算成绩」，学生问卷排第一的是「自动算分（77.78%）」——**两个独立来源指向同一点**。
- 学生问卷里 66.67% 想要「判断某项经历符不符合加分条件」，辅导员最关心的第一条是「正确识别加分材料」——**同一个点的两面**。

（说明：访谈各只有 1 人，不能当定量证据。但它和学生问卷方向一致，**这让我们对这个判断更有信心**。）

而现有系统最用力做的「提交申请 + 查看审核进度」，在学生问卷里**排第 7（46.67%）**，辅导员和学生会**都没有提到**。

> **一句话**：大家要的是**算得准、看得懂、能规划**；系统做的是**把申请收上来**。

这不是功能太少，是**站位不对**。系统站在"流程流转"上，而三个使用者站在"结果可信"和"过程可预期"上。

**好在不用推翻重做，而且有一个共同的发力点：**

三边需求拆开看，底下是同一块地基——**把保研条例变成结构化、可读、可计算的规则。**

- 辅导员要材料识别准、核算可靠 → 前提是规则**统一、不含糊**
- 学生要能看懂条例、知道自己能加多少 → 前提是规则**能被读懂**
- 学生会要输入条例自动换算 → 前提是规则**能被机器读懂**

系统里「规则 → 系数 → 分数」的引擎已经跑通，这是现成优势；缺的是引擎前面那层。**补上它，一次改动同时服务三方。**

## 3.3 改进路线

**第一阶段 · 让用户算得清、看得懂**

- 规则通俗化：选规则时用人话讲清"这条要求什么、能加多少"
- 事前判断：用户填一项经历，系统当场告诉他符不符合、要不要补材料

这是学生问卷里第一和第二的诉求，也是辅导员"材料识别准"和学生会"自动换算"的共同前提。**不动数据库**，主要是在现有引擎前面补交互层。风险最低，见效最直接。

**第二阶段 · 把交互从事后提到事前**

- 截止时间与政策更新提醒
- 材料集中管理：证书、成绩单统一归档，申报时直接取
- 与目标要求的差距对比
- **历年保研信息**（比例、去向）与**保研流程、时间线展示**——这两项现有系统完全没有，但对"还没到申报期"的同学价值最大

**第三阶段 · 优化申报审核本身的效率**

- 审核弹窗加分页、审完自动跳下一条
- 报表支持排序、显示未通过项目、补上动态系数与志愿总时长
- 修复管理员改不了用户账号
- 允许学生删除未通过的申请

**为什么放最后**：调研里排第 7，且学生问卷覆盖不到教师端。在拿到教师侧反馈之前，不宜投入最多资源。但分页这类改动成本极低，可以顺手做掉。

**第四阶段 · 原项目标注「需大改」的部分**

- 四六级、绩点改为「学生传材料 → 教师审核确认」
- 志愿时长改为「管理员配算式 → 学生只填时长 → 系统自动算」，并支持多次申报累计
- 规则提供默认模板
- 项目数与分数上限真正落地，允许超额申报后自动取最高分前 N 项

**为什么放最后**：这几项要动数据模型、审核状态机和计算逻辑，投入产出比最需要谨慎评估。建议在前两阶段验证过用户反馈之后再定。

## 3.4 要主动交代的两点

**学生问卷样本有偏。** 45 份里大一加大二占 88.89%，大三只有 2 人。而保研申报主要发生在大三下到大四。所以这部分数据反映的是"还没到申报期的人"的预期与焦虑，不是"正在申报的人"的实际操作反馈。

**两次访谈的样本量都只有 1 人**——辅导员 1 人（线上）、学生会学长 1 人（线上）。它们属于探索性访谈，作用是发现问题和形成假设，**不作为定量结论**。报告里应当明确写成"访谈"，而不是"调研样本"。

# 安全保障方案与技术路线

系统里存着学生的成绩、排名、加分材料和个人信息，还要开放到公网。安全上主要防三件事：机器人脚本、数据爬取、漏洞入侵。

下面按这三类分别给方案，最后是技术路线和落地顺序。

---

## 一、反机器人

机器人的特征是快、齐、重复。对策分三层。

**第一层，限流。** 同一来源在单位时间内只能请求 N 次。用 Flask-Limiter 加个装饰器就行，登录这类接口设 5 次/分钟，第 6 次开始返回 429。这一条我们实际跑过，确实生效。

**第二层，Proof-of-Work 验证码。** 传统图形验证码的问题是：人也要费劲辨认，而机器人反而能打码。PoW 换了个思路，让浏览器算一道题——用户无感，但每次请求都要真实算力。用 mCaptcha，Rust 写的，可以自托管，不依赖商业服务。只加在登录、注册、批量导出这些动作上，不要全站都加。

**第三层，蜜罐字段。** 表单里藏一个正常用户看不见的输入框。真人不会填，脚本会无脑填满所有字段——一旦有值就判定为机器人。几行代码的事，成本几乎为零。

## 二、反爬

反爬没有单一神器，得靠组合。而且真正有效的几招都不是技术对抗，是减少数据暴露面。

**越权校验最重要。** 限流挡不住"用合法身份慢慢爬"。每次取数据都要校验这条数据属不属于当前用户。具体到我们：学生改 URL 里的 ID 不能看到别人的申请；教师只能看本院本系的；列表接口必须服务端按身份过滤，不能靠前端传 facultyId 参数。这一条同时也是反侵入里最重要的越权防护，一份工作两个收益。

**分页硬上限成本最低。** 禁止 pageSize=99999 这类请求，单次最多返回 20 到 50 条。爬虫拿数据的速度会被直接压到和正常人一样。

**数据脱敏。** 排名列表给学号、姓名、排名就够了，不给身份证、手机号和材料明细；申请详情里看别人的申请只给状态。

**限流加行为检测。** 请求间隔过于均匀、UA 固定不变、缺 Referer，都可以标记为可疑。但只靠 User-Agent 判断爬虫是无效的，一行代码就能伪装，不能当主要手段。

**访问日志。** 记录谁在什么时候批量拉了什么。爬取行为事后一定看得出来，有日志才能追溯和举证。

## 三、反黑客反侵入

这是投入产出比最高的一块，挡的是能直接拿到权限的攻击。

**先装应用层三件套。** 这三个库加起来不到 20 行代码，我们实际装上去跑过：

- flask-talisman 管安全响应头，一行代码，CSP、防点击劫持、防 MIME 嗅探全有
- Flask-SeaSurf 管 CSRF，防止有人构造页面诱骗已登录的教师完成审核
- Flask-Limiter 管限流

**网络层用 OWASP Coraza 加 CRS 规则集。** 应用层三件套覆盖不到扫描器、已知漏洞利用、路径穿越、命令注入这些，得靠 WAF。Coraza 是 OWASP 社区的开源 WAF 引擎，Go 实现，是 ModSecurity 的现代替代品；CRS 是 OWASP 维护的通用攻击规则集，覆盖 SQL 注入、XSS、路径穿越、常见扫描器，直接用，不用自己写规则。Nginx 接入用官方连接器。

**业务代码层必须自己写对的几条：**

- SQL 全程走 ORM 或参数化查询，永远不拼接字符串
- 越权校验，见上面第二条
- 文件上传五条校验，见下
- 用户输入输出时转义，防 XSS
- 密码强度校验加登录失败锁定
- 密钥从环境变量读，不进代码库

文件上传这块要单独说，因为我们的系统要收证明材料，这是最危险的入口。五条：白名单扩展名；文件头嗅探，不能只信 MIME 和扩展名；重命名，不用用户提交的文件名，防路径穿越；存到 Web 根目录之外，通过受权限控制的接口读取；服务器上绝不能把上传目录配成可执行。

**主机层用 CrowdSec。** 读 Nginx 和应用日志，识别爆破和扫描行为，自动下发防火墙规则封 IP。

**CI 里跑三个扫描工具。** Bandit 扫 Python 代码，Semgrep 做多语言静态分析，Trivy 扫依赖漏洞和容器镜像。

**写代码时对照 OWASP Top 10。** 重点看「失效的访问控制」和「注入」两节。

## 五、部署层次

```
用户浏览器
    ↓
[Nginx]
    ├── limit_req / limit_conn      粗粒度限流
    ├── Coraza + OWASP CRS          通用攻击拦截
    └── 反向代理
         ↓
[Flask 应用]
    ├── Talisman       安全响应头
    ├── SeaSurf        CSRF 校验
    ├── Limiter        接口级限流
    ├── 越权校验        每个取数接口
    ├── ORM 参数化      防注入
    └── 上传五条校验    防文件上传漏洞
         ↓
[数据库]
    ↓
[CrowdSec] 读日志，自动封 IP
```

对应的接口：

| 接口 | 措施 |
|---|---|
| /api/login | 严格限流 + PoW 验证码 + 失败锁定 + CSRF |
| /api/register | PoW 验证码 + 限流 |
| /api/applications（提交） | 上传五条校验 + 限流 |
| /api/applications/<id> | 对象级越权校验 |
| /api/applications/<id>/review | CSRF token + 角色校验 |
| /api/students/ranking | 分页硬上限 + 脱敏 + 严格限流 |
| /api/rules、/api/admin/* | 管理员角色校验 + 审计日志 |

## 六、技术难点

**校园网 NAT。** 这是我们最特殊的一个问题。全校学生很可能共用少数几个出口 IP，如果按 IP 限流，结果是**一个人脚本刷，整栋宿舍楼被封**。限流维度必须改成「IP + 账号 + 接口」的组合：未登录接口用 IP 限流但放宽阈值，已登录接口用账号维度。而且阈值不能拍脑袋定，得先记录一周真实的 QPS 分布。

**SeaSurf 会拦住所有 POST。** 这个是我们实际装上去才发现的：加了 SeaSurf 之后，登录接口也返回 403，因为请求里没有 CSRF token。对纯 JSON API 来说必须处理——前端得先从响应的 _csrf_token cookie 拿到 token，再在请求头带 X-CSRFToken；或者对确实不涉及会话状态的接口做豁免。不能装上就不管，否则整套接口全废。

**WAF 规则会误杀。** OWASP CRS 默认规则偏严格，直接开 Paranoia Level 1 就可能拦掉正常请求，比如项目名里带 SQL 关键字、规则说明里有尖括号。必须先跑 DetectionOnly 模式只记日志不拦，看清楚哪些是误判，再逐步收紧。

**验证码和体验有矛盾。** 教师审核是高频操作，每步都弹验证码会被骂。只给风险动作上验证码，已登录的常规操作不加。mCaptcha 的 PoW 本身就是无感的，这里最合适。

**HSTS 和本地开发冲突。** Talisman 在 force_https=False 时不会下发 HSTS 头，这是对的，本地跑 http 时带了反而会被浏览器强制跳 https。生产环境记得改成 true。

**真正的成本在维护不在部署。** 开源安全组件装起来不难，难的是长期有人负责：CRS 规则要更新，CrowdSec 告警要有人看，扫描报告要有人处理。第一周不要贪多。

## 七、技术路线

### 阶段一（当周）：零新组件，改代码就能做完

装 flask-talisman，装 Flask-SeaSurf，前端配合带 X-CSRFToken（这一步不做，接口会全废），全面核查越权，文件上传五条校验，生产环境关掉 debug 并把密钥挪进环境变量，确认密码用的是 bcrypt 或 argon2。

这批不需要引入任何新服务，改动全在自己代码里，出问题好回滚，而且堵的都是能直接拿权限的洞。

### 阶段二（一周内）：引入限流和验证码

装 Flask-Limiter，配 Nginx 的 limit_req，接 mCaptcha 到登录和注册，表单加蜜罐字段。

这一阶段还有一件不是开发的事：**记录一周真实的 QPS 分布**。校园网 NAT 那个难点的阈值必须靠真实数据定。

### 阶段三（需要专门投入）：WAF 和运维

部署 Coraza 加 CRS，先跑 DetectionOnly，分析误判调 Paranoia Level，正常业务请求零误杀之后再切拦截模式。部署 CrowdSec。CI 里集成 Bandit、Semgrep、Trivy。指定一个安全负责人。

放最后的原因是：在没有专人负责之前上线 WAF，只会得到一个装了就没人管的摆设。

## 八、已经验证过的部分

我们建了个干净环境实际跑了一遍，版本是 Flask 3.1.3、flask-talisman 1.1.0、Flask-Limiter 4.1.1、Flask-SeaSurf 2.0.0。

**Talisman 响应头。** CSP、X-Frame-Options、X-Content-Type-Options、Referrer-Policy 都正常下发。HSTS 没下发，因为设了 force_https=False，符合预期。

**限流。** /api/ranking 设 5 次/分钟，连打 7 次：前 5 次 200，第 6、7 次 429。限流生效。

**CSRF。** 不带 token 的 POST 返回 403；响应里下发了 _csrf_token cookie，前端可以据此取 token。同一个请求打登录接口也返回 403，这就是上面那个难点的来源。

验证用的最小工程在 `security-demo\`，里面是 app.py 和 _verify.py，复现方式是建 venv、pip install 四个包、跑 python app.py，再跑 _verify.py。

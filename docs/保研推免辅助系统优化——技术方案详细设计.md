
## 0. 现状技术架构与数据流

|层|技术|关键文件|
|---|---|---|
|前端|Vue 3 + Pinia + Vue Router|`frontend/views/`、`frontend/components/`|
|后端|Flask + SQLAlchemy|`backend/blueprints/*.py`|
|数据|SQLite（`instance/gradpush.db`）|`backend/models.py`|

**核心数据流（当前）**：

```
学生提交申请 → Application 表(status=pending) → 教师审核 review_application()
    → 自动/手动确定 final_score → update_student_statistics()
    → 汇总到 Student 表 → 排名展示
```

**源码阅读发现的关键缺陷**（这是本次优化的技术依据）：

1. `review_application()` 中"最大项目数量"判断有重复条件 Bug，导致 `max_count` 限制**永远不生效**（[application_bp.py:858-863](vscode-webview://119fefd5faoj2u1ume373f4ol70b0lulhigp4oioe0ifiim7je73/%E4%BF%9D%E7%A0%94%E6%8E%A8%E5%85%8D/GradPush/backend/blueprints/application_bp.py#L858-L863)）。
2. 动态系数被写成 `final_score *= application.dynamic_coefficients`，而 `dynamic_coefficients` 是**字典对象**，字典×数字会报错，导致"动态系数"功能**形同虚设**（[application_bp.py:877-879](vscode-webview://119fefd5faoj2u1ume373f4ol70b0lulhigp4oioe0ifiim7je73/%E4%BF%9D%E7%A0%94%E6%8E%A8%E5%85%8D/GradPush/backend/blueprints/application_bp.py#L877-L879)）。
3. `RuleCalculation`（算式计算模型）**已定义但从未在审核逻辑中真正使用**，四六级/绩点只能由管理员在后台直接改。

## 1. 问题A：成绩自动计算体系（需大改，优先级最高）

### A1 四六级 / 绩点：改为「学生上传 → 教师审核」

**现状**：`Student` 表已有 `cet4_score / cet6_score / gpa` 字段，但只能由管理员在 `update_student()` 里直接写入，学生无法参与，教师端无审核入口。

**数据库改动**（`models.py`）：

- `Application` 表无需大改，复用现有 `files`（JSON 数组）存材料附件，新增一个标识字段即可区分材料类型。
- 新增枚举/标识：`material_type`（`cet4` / `cet6` / `gpa`），或通过 `rule_id` 关联到"四六级加分规则"来识别。

**后端改动**（`application_bp.py` + `score_bp.py`）：

- 学生提交时，走现有 `create_application()`，带上成绩材料附件。
- 教师审核时，在 `review_application()` 中增加分支：若申请类型为四六级/绩点，教师填写**认定成绩**（`final_score`），保存到 `Application.final_score`，同时回写 `Student.cet4_score / cet6_score / gpa`。

**前端改动**：

- `components/student/ApplicationForm.vue`：增加"四六级/绩点"申请类型，上传成绩单附件。
- `components/teacher/PendingReview.vue`：增加成绩认定输入框。

### A2 志愿时长：独立算式，自动计算加分

**现状**：学生需手动填 `self_score`（自评分），无志愿时长字段，无算式计算。

**数据库改动**（`models.py`）：

- `Application` 新增字段 `volunteer_hours = db.Column(db.Float, nullable=True)`（志愿时长，单位：小时）。
- 复用 `RuleCalculation` 现有结构：`calculation_type="formula"`，`formula="hours * coefficient"`，`parameters={"coefficient": 0.5}`。

**后端改动**（`application_bp.py`）：

- 学生提交时只填 `volunteer_hours`，**不填自评分**。
- `review_application()` 审核通过时，解析规则的 `formula`，代入 `hours` 变量计算 `final_score`（如 `50 小时 × 0.5 = 25 分`）。
- "申请一次加一次"：每次志愿服务单独一条 `Application`，`update_student_statistics()` 里天然累加。

**算式解析（核心算法）**：

```python
def calc_volunteer_score(formula, parameters, hours):
    # formula: "hours * coefficient"，parameters: {"coefficient": 0.5}
    expr = formula.replace("hours", str(hours))
    for k, v in parameters.items():
        expr = expr.replace(k, str(v))
    return round(eval(expr, {"__builtins__": {}}, {}), 2)  # 白名单安全求值
```

> 注：`eval` 需用空 `__builtins__` 白名单防止注入，或改用简单解析器（只支持 +、-、*、/）。

**前端改动**：

- `ApplicationForm.vue`：志愿类项目只显示"志愿时长"输入框，隐藏自评分。
- `RuleManagement.vue`：管理员配置算式（系数、单位）。

### A3 规则「最大数量/分数限制」真正生效

**现状 Bug 分析**（[application_bp.py:858-863](vscode-webview://119fefd5faoj2u1ume373f4ol70b0lulhigp4oioe0ifiim7je73/%E4%BF%9D%E7%A0%94%E6%8E%A8%E5%85%8D/GradPush/backend/blueprints/application_bp.py#L858-L863)）：

```python
Application.student_id == application.student_id,
Application.application_type == "academic",            # ← 条件1
Application.application_type == application.application_type,  # ← 条件2 矛盾
```

两个条件同时要求 `application_type` 既等于 `"academic"` 又等于自身，导致 `approved_count` 恒为 0，`max_count` 限制失效。

**修复方案**：

1. **修 Bug**：删除重复条件，只保留 `Application.application_type == application.application_type`。
2. **改进逻辑**（对应 Problems.md 需求"允许超出后自动选最高分前 N 项"）：
    - 审核通过时**不再**把超出项目判 0 分，而是允许所有项目通过。
    - 在 `update_student_statistics()` 里，对同一学生、同一规则下的已通过项目**按分数降序排序，只取前 N 项**（N = 规则 `max_count`）计入总分。
    - 前端报表标注哪些项目"已入选"、哪些"超出名额未计入"。

**后端改动**（`score_bp.py`）：

- 重写 `update_student_statistics()`：按 `rule_id` 分组 → 每组排序 → 截断前 N 项 → 累加。
- 修 `review_application()` 的动态系数 Bug：改为正确解析 `dynamic_coefficients` 字典（如 `{"level_factor": 1.2, "grade_factor": 1.0}`，相乘后应用到分数）。

## 6. 关键技术难点与对策

|难点|对策|
|---|---|
|算式解析安全性|算式求值用**白名单**（只允许数字、+、-、*、/、括号），禁用任意 `eval`|
|数据库迁移|SQLite 本地用 `db.create_all()` + 手动 `ALTER` 补字段；上线前迁移到 PostgreSQL 用 `flask db migrate`|
|老数据兼容|新增字段全部设 `nullable=True`，老记录不报错|
|前后端字段名不一致|沿用现有 `transformFieldNames`（驼峰↔下划线）机制|

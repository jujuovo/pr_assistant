# 下一次 OpenSpec propose 前规划

更新日期：2026-11-05

## 推荐主题

建议下一次 change 聚焦“当前推免周期内审核后计分反馈闭环”，候选名称：

`close-cycle-scoring-feedback-loop`

本文件是 propose 前规划，不是 proposal，也不创建新的 active change。

原建议 `complete-ranking-batch-operations` 顺延。原因不是排名运营不重要，而是正式排名必须建立在可靠的计分事实和学生汇总快照之上；当前已经复现“教师审核通过并设置 5 分，但学生端仍显示 0”的核心链路缺陷，必须先解决。

## 用户问题与目标结果

### 已复现的问题

学生通过“提交项目 -> 科创竞赛”上传蓝桥杯奖状，完成 OCR 核对并提交；教师审核时给出终审分数 5 并通过。切换回 `student001` 后，学生端“我的项目”中的单项加分和总分仍为 0。

这不是单纯的显示问题。代码证据表明，当前链路可能在审核成功、规则版本、计分周期和学生读取年度之间断裂：

- 本地 seed 创建 `Rule`，但没有保证存在可供计分绑定的已发布 `RuleVersion`；
- 兼容申请找不到规则版本时可返回 `scoring.status = needs_rule`，但审核接口仍可能表现为整体成功；
- 蓝桥杯兼容申请使用 `award_date.year` 推导计分年度；
- 学生端读取快照时使用的年度语义与推免周期尚未统一；
- 因此可能不生成 `ScoreEntry` 或 `StudentScoreSnapshot`，最终出现“审核通过但分数为 0”的假成功。

### 目标结果

建立一条后端权威、原子、可解释的闭环：

```text
奖状事实日期
  -> 当前推免周期全局有效期校验
  -> 教师审核材料真实性
  -> 已发布规则版本自动计分
  -> 必要时有审计地人工改写
  -> 生成/更新 ScoreEntry
  -> 重建当前周期 StudentScoreSnapshot
  -> 使相关 draft 排名失效
  -> 学生看到单项分、计入状态、原因和周期总分
```

系统不得再出现“材料显示审核成功，但计分因缺少规则、周期错误或快照失败而静默保持 0”的结果。

## 苏格拉底式问诊已经确认的业务决策

以下内容视为本 change 的已确认输入，不应在 proposal 中重新默认为开放问题：

1. `award_date` 是证据事实发生日期，不是推免计分周期年度。
2. 奖状是否可计分，取决于 `award_date` 是否落在当前推免周期统一的全局有效日期区间。
3. 同一时刻系统只处理一个活动推免周期。
4. 所有学院共用同一个活动推免周期。
5. 所有竞赛共用同一个奖状有效日期区间，不由每条竞赛规则分别设置。
6. 分数默认由不可变的已发布规则版本自动计算。
7. 约 90% 的材料中，教师只审核真实性，不改写系统计算分数。
8. 教师可以在授权范围内改写分数，但必须保存自动计算值、改写值、理由、操作者和时间。
9. 缺少规则版本、资格无法判定或快照重建失败时，不得把操作呈现为完整审核成功。
10. 排名批次年度应与计分快照所属推免周期一致，不应由奖状年份决定。

## 建议的权威概念与职责

### 1. 活动推免周期

`SystemSettings.academic_year` 或等价的全局周期配置应升级为唯一活动推免周期的权威来源，但不能只作为动态标签读取：

- 新申请或材料在创建/提交时固定 `application_cycle_year`；
- 后续审核、重算和历史读取使用已固定周期，不随系统当前周期切换而改变；
- `ScoreEntry.year`、`StudentScoreSnapshot.year` 和后续 `RankingBatch.year` 使用该周期；
- 历史记录不得因重新读取当前设置而被归入新周期。

字段最终放在 `Application`、兼容适配记录还是统一来源上下文中，由 design 根据渐进迁移约束决定；proposal 应先固定语义，不把某个字段名提前当成唯一方案。

### 2. 奖状有效日期区间

推免周期应拥有明确的全局 `eligible_award_start_date` 与 `eligible_award_end_date`，或语义等价的版本化政策快照：

- `award_date` 只与该区间比较；
- 区间包含性、时区和边界日期必须固定；
- 审核计分时保存所使用的区间快照或政策版本；
- 后续修改全局设置不得静默改变历史计分结果；
- 申请开放时间不得冒充奖状有效期。

### 3. 规则版本

- 自动计分只能绑定不可变、已发布且适用于当前周期的 `RuleVersion`；
- seed、初始化和规则启用流程必须保证可演示规则具有已发布版本；
- 缺少适用版本时返回明确阻塞结果，不得默认记 0，也不得完成“已审核且已计分”的成功语义；
- 新规则发布不得静默重算旧明细，重算必须有范围、预览和审计。

### 4. 教师审核与分数改写

默认流程为“教师确认核验结论，系统按规则计算”，而不是“教师手工填写最终分数”。若教师改写：

- 后端重新校验改写权限和允许范围；
- 改写理由必填；
- 保存规则自动分、改写分、差值、理由、操作者、时间和关联审核版本；
- 学生计分解释能够区分规则自动分与人工改写结果；
- 重试不得生成重复改写记录或重复入分。

## 建议范围

### 后端业务与数据

1. 建立唯一活动推免周期及全局奖状有效日期区间的权威配置与校验。
2. 在申请创建或提交时固定推免周期；禁止用 `award_date.year` 作为 `ScoreEntry.year`。
3. 为旧 `Application`/证书兼容路径提供明确的周期归属，继续通过统一计分适配器进入 `ScoreEntry`。
4. 保证规则启用、seed 和本地准备流程创建或绑定不可变的已发布 `RuleVersion`。
5. 将资格判断、规则自动计分和教师改写建模为可解释结果，不以 0 混淆“规则结果为零”和“未成功计分”。
6. 审核、计分明细、改写审计、学生快照和相关 draft 排名失效在一个后端事务中提交。
7. 使用材料/申请版本与幂等键处理并发和超时重试；相同键不同请求内容必须拒绝。
8. 对已通过但缺少 `ScoreEntry`、周期错误或快照缺失的历史申请提供 dry-run 对账和幂等修复路径。
9. 保留原始奖状日期、OCR 结果、教师结论、规则版本和历史分数，不静默覆盖证据或正式历史。

### API 契约

1. 审核响应明确区分：
   - `scored`：审核与计分完整成功；
   - `verified_not_eligible`：材料真实性通过，但日期不符合本周期计分资格；
   - `needs_rule`：缺少适用的已发布规则版本；
   - `override_required` 或等价状态：自动结果需要授权人工处理；
   - `failed`：核心事务失败并已整体回滚。
2. “审核结论”和“计分结果”分别返回，前端不得把 `verified` 自动解释为已获得分数。
3. 计分响应至少包含周期、证据日期、资格区间/政策版本、规则版本、自动分、改写分、有效分、计入状态、排除原因和快照更新时间。
4. `needs_rule`、资格不明或快照失败使用可识别错误/阻塞契约；不得仅返回 HTTP 200 和笼统的“审核成功”。
5. API 返回后端计算的 `allowed_actions`，前端不自行推导教师是否可以改写或重试计分。

### 前端

1. 教师审核页面默认展示规则自动计算结果，主要操作是核验通过、补正或拒绝。
2. 人工改写作为次级、受权限保护的显式操作，要求理由并展示原自动分与改写后分数。
3. 缺少规则、日期不合格或计分失败时，教师端展示具体阻塞原因和下一步，不显示完整成功提示。
4. 学生“我的项目”展示每个项目的材料状态、计分状态、规则依据、自动/改写结果、实际计入分和未计入原因。
5. 学生总分从当前活动推免周期的权威 `StudentScoreSnapshot` 读取，不使用当前自然年或多个旧字段回退猜测。
6. 页面明确区分“材料已核验但不符合计分资格”“等待规则处理”“已计入”和“未计入/被封顶”。
7. 保留 OCR 失败后的人工审核路径，OCR 结果不决定资格、审核结论或最终分数。

### 迁移与兼容

1. 盘点没有周期字段的现有 `Application`，制定可解释的周期映射规则；无法确定的记录进入人工清单，不用 `award_date.year` 静默猜测。
2. 扫描 `approved` 但无有效 `ScoreEntry`、有 `ScoreEntry` 但无当前快照、快照年度异常的记录。
3. 修复前提供 dry-run 报告，按申请、学生和周期列出差异及建议动作。
4. 修复命令必须幂等、支持失败隔离与续跑，并保存批次和来源审计。
5. 旧 `final_score` 与学生旧汇总字段在兼容期作为投影保留，不再成为新权威输入。
6. 对账未清零前不得将受影响范围用于正式排名发布。

## 明确不纳入

- 不建设排名批次列表、创建、冻结、发布、撤回的完整运营页面；该主题顺延至 `complete-ranking-batch-operations`。
- 不重写排名算法或 `RankingBatch`/`RankingEntry` 模型。
- 不完成五类材料的完整动态表单。
- 不接入志愿工时学生页面。
- 不扩展通用 OCR，也不让 OCR 自动认定真实性或加分。
- 不删除 `Application`、旧成绩字段或历史数据。
- 不进行全站视觉重构、微服务拆分或消息队列改造。

## 必须覆盖的验收场景

### 主验收场景：蓝桥杯正常计分

- **GIVEN** 当前活动推免周期及全局奖状有效区间已配置，蓝桥杯存在适用的已发布规则版本，奖状日期位于有效区间内
- **WHEN** `student001` 上传蓝桥杯奖状、确认 OCR 并提交，教师不改写分数而审核通过
- **THEN** 系统按规则自动得到 5 分，在同一事务中生成计分明细与当前周期快照，学生“我的项目”显示该项目计入 5 分且总分同步更新

### 缺少规则版本

- **GIVEN** 材料真实且日期合格，但没有适用的已发布 `RuleVersion`
- **WHEN** 教师尝试审核通过
- **THEN** 系统返回 `needs_rule` 阻塞，不生成有效分数或新快照，不显示“审核并计分成功”，且不留下部分成功

### 奖状日期不符合资格

- **GIVEN** 奖状真实但 `award_date` 位于全局有效区间外
- **WHEN** 教师确认材料真实性
- **THEN** 系统保留核验事实并明确标记“不符合本周期计分资格”，不生成有效加分，不把原因显示成教师拒绝或计算故障

### 教师有审计地改写

- **GIVEN** 已发布规则自动计算为 5 分，教师具有改写权限
- **WHEN** 教师填写理由并改写为 4 分
- **THEN** 系统保存自动分 5、改写分 4、理由、操作者、时间和审核版本，学生看到实际计入 4 分及人工调整标识，重试不会重复入分

### 周期与事实日期解耦

- **GIVEN** 当前推免周期为 2026，合格奖状的 `award_date` 为 2024
- **WHEN** 材料审核计分成功
- **THEN** `ScoreEntry` 与 `StudentScoreSnapshot` 归属 2026 推免周期，同时保留 2024 奖状事实日期用于资格解释

### 核心事务回滚

- **GIVEN** 材料与规则均合法
- **WHEN** 保存计分明细后快照重建失败
- **THEN** 审核结论、计分、改写审计、快照和排名失效标记整体回滚，客户端得到可识别失败结果

### 历史修复

- **GIVEN** 历史申请为 `approved` 且 `final_score = 5`，但缺少有效 `ScoreEntry` 或快照
- **WHEN** 管理员先执行 dry-run、确认范围后运行修复
- **THEN** 系统按固定周期和规则版本幂等生成结果，重复执行不重复入分，无法解释的对象进入人工清单

## 验证要求

1. 后端测试覆盖周期固定、有效期边界、规则版本缺失、自动计分、改写审计、幂等、并发版本冲突和事务回滚。
2. 增加契约测试，确保 `verified`、`scored`、`needs_rule`、`verified_not_eligible` 等语义不会被混淆。
3. 前端 service/store 与组件测试覆盖成功、阻塞、人工改写和学生单项/总分展示。
4. 浏览器旅程覆盖上述蓝桥杯主场景，并验证刷新后结果仍来自权威快照。
5. 运行现有证书 OCR、材料审核、计分、自动化、排名失效和旧接口兼容回归。
6. 在隔离 SQLite 数据库执行迁移、dry-run、修复与重复运行验证。
7. 在目标 PostgreSQL 主版本验证约束、事务和两个并发审核请求只有一个成功。
8. 运行后端完整回归、前端测试、生产构建和 OpenSpec strict validation。

## 仍需在 propose/design 中明确的问题

以下问题不会改变本 change 的优先级，但会影响具体设计，不能静默假设：

1. `academic_year` 的格式与含义：使用自然年整数 `2026`，还是学年标识 `2025-2026`；它如何映射到排名年度。
2. 全局有效日期区间的边界是否包含起止日，以及周期切换时如何版本化和保留历史政策。
3. 哪些教师角色拥有改写权限，改写是否有最大范围限制，是否需要管理员二次复核。
4. 不符合日期区间的材料是否仍使用 `verified` 并附加计分资格结果，还是需要独立核验结论；推荐保持“事实核验”和“计分资格”分离。
5. 对已审核但 `needs_rule` 的记录，是保持待处理状态、回退待审核，还是保存核验事实并单独阻塞计分；推荐保存核验事实，但不得声明完整审核计分成功。
6. 历史无周期申请的默认映射证据来自哪里；无法证明时必须人工处理。

## 风险与门禁

- 最大风险是只修正页面或 seed，使演示场景暂时出现 5 分，却继续保留错误的年度语义和假成功契约。
- 活动周期是全局配置，但历史记录必须固定周期；否则切换年度会静默改变旧申请的读取与重算结果。
- 教师改写若直接覆盖自动分，会破坏规则可解释性和审计链。
- `needs_rule` 不得降级为 0 分，也不得由前端忽略。
- 历史修复必须先 dry-run；无法解释的数据不得自动猜测归属周期或规则版本。
- 本 change 完成前，不应继续扩展正式排名发布入口。

## 退出条件

出现以下任一情况，应暂停本 change 并重新定界：

- 业务方否认“同时只有一个全局活动推免周期”；
- 不同学院需要不同周期或不同奖状有效区间；
- 教师手填分数而非规则自动计分才是正式权威流程；
- 无法获得奖状有效区间或规则版本的权威来源；
- 蓝桥杯流程实际不应进入统一 `ScoreEntry`/快照链；
- 历史数据无法确定周期归属，且业务方要求自动修复而不允许人工清单。

## 后续 change 候选顺序

1. `close-cycle-scoring-feedback-loop`：本规划推荐的下一次 propose。
2. `complete-ranking-batch-operations`：计分反馈与对账稳定后，完成排名批次运营闭环。
3. `complete-structured-material-workbench`：五类材料创建、编辑、附件、补正和事件时间线。
4. `integrate-volunteer-student-workflow`：志愿材料上传、识别轮询、逐项确认和提交页面。
5. `retire-legacy-score-projections`：只有旧消费者归零、连续对账一致后才可提出。

## 第一步行动

以本文件为发现输入，运行：

```text
/openspec-propose close-cycle-scoring-feedback-loop
```

proposal 必须以“蓝桥杯审核后学生仍显示 0”的已复现路径作为首要用户问题，并把“奖状事实日期与推免计分周期解耦”“缺少规则版本时禁止假成功”“规则自动计分与有审计改写”“学生单项与总分反馈”列为同一闭环的必要组成，而不是拆成互不一致的页面补丁。
